# 02 · 密钥从哪里来

## 结论

对局对称密钥**不是**在对局通道里协商出来的，而是在建立连接阶段被"告诉"客户端的。

两条安装路径：

```
路径 A  DTLS 握手完成 → HKDF 派生 → 装入 16 字节密钥
路径 B  连接信息结构体 + 偏移处的字符串 → 直接装入
```

两条都在连接建立时执行，且会话期内会周期性轮换。

## 路径 B：连接信息里的字符串

网络通道建立函数里，决定使用哪个加密上下文：

```
mov  rcx, [channel + 0x32E8]     ; 连接自带的上下文
test rcx, rcx
jne  use_it
lea  rcx, [global_default_ctx]   ; 否则用全局默认
use_it:
    call encrypt_wrapper
```

上下文从哪里来：

```
mov  rdx, [conn_info + 8]        ; 结构体里的一个字符串字段
cmp  byte [rdx], 0
je   use_default
call install_key                 ; 非空就装成密钥
```

结构体布局（观察到）：

```
+0x00  标志
+0x08  密钥字符串（非空则安装）
+0x10  另一个字符串
+0x20  指针
```

这个结构正是"服务器列表条目"式的设计：每台服务器带一个密钥，
客户端连接前把它装上。

## 路径 A：DTLS + HKDF

DTLS 路径的实现里：

```
call hkdf                     ; 输出 32 字节，salt 13 字节
call install_key              ; 装 16 字节
call base64_encode            ; 编码成 24 字符，用于上报
call telemetry("...new_key")
```

内置默认密钥是一个 24 字符的 base64 常量（16 字节），
仅在未收到服务器密钥时作为兜底。

## 密钥轮换

明文遥测（见 `06`）里能看到会话期内多次 `new_key` 事件：

```
t+0.4s    session
t+84s     new_key
t+84s     session
t+132s    new_key
t+132s    session
t+738s    new_key
t+738s    session
```

⇒ 密钥不是整局固定，而是周期性轮换的。

## 为什么这决定了可行性

密钥是**下发**的，不是**协商**出来的对称结构。这意味着：

| 观察者的位置 | 能否拿到密钥 |
|---|---|
| 网线上的被动旁听 | ✗ 密钥在认证 TLS 里 |
| 网关（能做中间人） | ✗ 证书固定 |
| 客户端进程内 | ✓ 但需要读内存，被反作弊拦 |

与某些游戏不同，这里不存在"TCP 控制通道做一次无认证 DH 即可中间人"的入口——
下发通道本身是带证书固定的 TLS。

## 结论

拿到密钥的所有路径最终都指向同一个问题：
**你能不能读到客户端进程的内存，或者能不能解开它的 TLS。**

前者见 `03`，两者都被实测关闭，见 `04`。
