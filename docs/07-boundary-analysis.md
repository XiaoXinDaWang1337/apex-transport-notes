# 07 · 边界分析：为什么只剩内核态与硬件两条路

> 这一篇只讨论**边界**——每道防线拦的是什么、下一层为什么能绕开。
> 不涉及可执行的绕过手段。

## 观测者能站在哪些位置

对一个受保护的游戏进程，观测者只有四个物理位置：

```
① 网线上（网关、交换机镜像口）
② 同一操作系统的用户态（另一个进程）
③ 同一操作系统的内核态（驱动）
④ 操作系统之外（PCIe 设备、虚拟机宿主）
```

`docs/04` 已经把 ① 和 ② 全部实测关闭。本文解释 ③ 和 ④ 为什么不同——
不是"更难"，而是**面对的是不同的机制**。

## ① 网线：终点是一把认证通道里的密钥

网关能看到全部字节，但字节是 AEAD 密文。解密需要密钥，密钥经 TLS 下发，
而 TLS 的证书固定使其无法中间人。

⇒ 这条路的问题不在"观测能力"，而在"密钥不在可观测范围内"。
任何再强的流量分析也改变不了这一点。

## ② 用户态：权限被逐项剥离

反作弊在进程对象上做了精细的访问控制：

| 请求 | 结果 |
|---|---|
| `PROCESS_QUERY_INFORMATION` | 放行 |
| `PROCESS_VM_READ` | 剥离 |
| `PROCESS_SET_QUOTA` | 剥离 |
| `PROCESS_SUSPEND_RESUME` | 剥离 |
| 模块枚举 | 拦截 |

关键点：**`OpenProcess` 本身是成功的**。被剥离的是句柄上的具体权限，
而不是句柄本身。这使得"打开就失败"这类判断全部失效。

⇒ 用户态的问题不是"没有找到正确的 API"，而是**权限模型在对象层面就不给你**。

## ③ 内核态：不同的主体

内核态代码不通过 `OpenProcess` 获取访问权，它可以直接构造内存访问。

这就绕开了 ② 的全部限制——不是因为找到了漏洞，而是因为**那道检查是针对
用户态进程句柄的**，对内核态的执行上下文不适用。

代价与风险：

- 加载第三方内核组件本身是可检测的事件（驱动列表、签名、加载来源）
- 需要与反作弊的驱动检测持续对抗
- 稳定性风险由自己承担（内核态崩溃影响整机）

⇒ 这是"军备竞赛"类方案：技术上成立，但维护成本随对手更新而上升。

## ④ 操作系统之外：不同的机器

DMA 类方案的物理形态是：设备通过 PCIe 直接读写系统物理内存，
**操作系统完全不知情**——没有句柄、没有进程、没有驱动、没有系统调用。

这绕开的不是"某一道检查"，而是**整个操作系统的观测面**。

但"绕过访问控制"不等于"拿到数据"。物理内存里没有"玩家坐标"这种东西：

```
物理内存
   └─ 页表（需要做虚拟→物理转换）
        └─ 进程地址空间
             └─ 游戏模块
                  └─ 实体列表结构
                       └─ 坐标字段（还需版本相关的偏移）
```

这四层每一层都要单独解决：

| 层 | 要解决的问题 |
|---|---|
| 物理层 | 采集设备与主机之间的读写通道 |
| 页表层 | 虚拟地址→物理地址转换（各代 CPU 的页表格式不同） |
| 进程层 | 定位目标进程的地址空间 |
| 结构层 | 实体布局、字段偏移、版本更新后的重新定位 |

⇒ 这类方案的工作量**不在"读取"，而在"定位与维护"**。而定位这一层，
恰好是本仓库 `docs/01` `docs/02` 的工作可以复用的地方：
一旦拿到明文，网络通道的解析器与内存结构的解析器面对的是同一套游戏逻辑。

## 一张对照表

| 位置 | 绕开什么 | 需要解决什么 | 维护成本 |
|---|---|---|---|
| ① 网线 | 无 | 密钥 | — |
| ② 用户态 | 无 | 权限（已被剥夺） | — |
| ③ 内核态 | 用户态权限模型 | 驱动检测、稳定性 | 高 |
| ④ 硬件 | 整个操作系统观测面 | 物理转换、进程定位、结构偏移 | 中（硬件固定后主要是偏移维护） |

## 结论

- ① 和 ② 是**已经关闭**的，而且关闭得很彻底（`docs/04`）
- ③ 和 ④ 不是"更厉害的技巧"，而是**换了主体**：一个以内核身份执行，
  一个根本不经过操作系统
- 只要不接受"在游戏机上增加内核组件或硬件"这个前提，
  这个问题的答案就是不存在解

这也是为什么本仓库把它写成一份**边界记录**而不是一份方案：
真正的分界线不在技术难度上，而在前提上。
